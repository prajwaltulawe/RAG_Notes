Langchain Part 11 - Vector Stores
Why Can’t We Use a Normal Database to Store Embedding Vectors?
1. The “Similarity” vs. “Equality” Problem
Traditional databases are built for Exact Matches (Equality).
•
Normal DB: You ask, “Find the user with ID 12345.” The DB uses a B-Tree index to find that exact number instantly.
•
Vector DB: You never ask for an exact match. You ask, “Find the 5 vectors most similar to this one.”
•
The Conflict: Standard databases aren’t designed to calculate “closeness” (Distance) between millions of rows simultaneously. To find the “most similar” item in a normal SQL table, the database would have to calculate the distance for every single row one by one, which is incredibly slow.
2. The Dimensionality Disaster
A standard database handles simple data: a string, an integer, or a date. An embedding vector is usually an array of 768 to 1,536 floating-point numbers.
•
High-Dimensional Space: When you have 1,536 dimensions, the math for “distance” (like Cosine Similarity or Euclidean Distance) becomes computationally “expensive.”
•
Index Failure: Traditional indexes (like B-Trees) work in 1D (sorting numbers from low to high). They completely break down when trying to index data in 1,000+ dimensions.
3. Specialized Indexing (ANN)
To make vector search fast, we use Approximate Nearest Neighbor (ANN) algorithms, such as HNSW (Hierarchical Navigable Small Worlds) or IVF (Inverted File Index).
•
The “Shortcut”: ANN indexes create a “social network” of vectors, allowing the search to “jump” through the most likely neighborhoods rather than checking every point.
•
Normal DBs: Most standard databases don’t have these complex “navigation maps” built into their core engine.
4. The “Hybrid” Evolution
It’s important to note that the world is changing. Because developers wanted to keep everything in one place, many “normal” databases have added Vector Extensions:
•
PostgreSQL has pgvector.
•
Redis and Elasticsearch now support vector fields.
The Catch: While these extensions are great for smaller projects, a Native Vector Database (like Pinecone, Milvus, or Weaviate) is still superior for massive scale because its entire architecture - from how it uses RAM to how it distributes data across servers - is “obsessed” with the math of high-dimensional vectors.
So we need a different type of database to store such embedding vectors.
Also, let’s say if we want to calculate similarity search for vector v1 and the rest of the vectors (let’s say there are 10 lakh vectors), then this becomes a computationally heavy task.
So instead of 10 lakh comparisons, we wish to do very few comparisons and obtain the top 5 vectors which are similar to vector v1, so we need an intelligent semantic search.
Another issue is we need to create the vector embeddings of each of these 10 lakh textual data.
Vector store helps us as it helps us to generate vector embeddings, it helps us with storage to store our vector embeddings, and gives us an option of intelligent semantic search.
What Are Vector Stores?
A vector store is a system designed to store and retrieve data represented as numerical vectors.
Key Features:
Storage
Metadata Integration
•
Regardless of whether you choose RAM or Disk, the Vector Store saves the Vector (the meaning) right alongside the Metadata (the “label” or “source”).
•
This ensures that when the AI finds a match, it immediately knows exactly which document or section that match belongs to.
Vector store gives us 2 options for storage. We can either store the vectors in-memory or on-disk.
1. In-Memory (RAM)
•
Speed: Extremely fast because the computer doesn’t have to “read” from a hard drive.
•
Durability: Temporary. If you turn off the computer or close the app, all the vectors are deleted.
•
Best For: Small projects, testing, or quick prototypes where speed is more important than saving data forever.
2. On-Disk (Hard Drive/SSD)
•
Speed: Slightly slower than RAM, but still very fast in modern systems.
•
Durability: Persistent. Your data is saved forever, even if the power goes out or the application restarts.
•
Best For: Enterprise-level applications and large-scale projects that need to handle millions of vectors over a long period.
When to Use Which?
•
Use In-Memory: If you are building a simple “one-off” tool or a small demo.
•
Use On-Disk: If you are building a professional tool that needs to remember data across different sessions and handle massive amounts of information.
Similarity Search
Helps retrieve the vectors most similar to the query vector.
Indexing
Provides a data structure or method that enables fast similarity searches on high-dimensional vectors (e.g., approximate nearest neighbor lookups).
Let’s look at one of the indexing algorithms used in vector stores:
•
Let’s assume in our vector store, we have 10 lakh vectors, where the dimension of each vector is 784.
•
Now we have a vector called v1, and we wish to find the top 5 vectors (from 10 lakh vectors) which are most similar to v1.
•
One way is to calculate similarity between v1 and each of the 10 lakh vectors, and then based on the similarity score, we can say which are the top 5 vectors closest to v1.
•
But this searching is linear and time complexity is O(n).
•
To solve this problem, we can use the concept of indexing. We’ll leverage clustering to address this issue.
•
We’ll cluster all these 1 million vectors using clustering algorithms, and let’s say we end up with 10 clusters, meaning each cluster contains 100,000 vectors.
•
Next, we’ll compute the average of all vectors in a given cluster, which gives us the centroid vector for that cluster.
•
So now we have 10 centroid vectors.
•
Whenever a new vector comes in and we need to find the most similar vector to it, we’ll calculate the similarity between this new vector and each of the 10 centroid vectors. Then, we’ll dive into the cluster with the most similar centroid and compute similarity between the new vector and all 100,000 vectors in that cluster.
•
This reduces our search space from 1 million to 100,000 vectors.
This is one indexing technique; another popular one is approximate nearest neighbor (ANN) lookups.
CRUD Operations
Manage the lifecycle of data: adding new vectors, reading them, updating existing entries, and removing outdated vectors.
Use Cases:
•
Semantic Search
•
RAG (Retrieval-Augmented Generation)
•
Recommender Systems
•
Image and Multimedia Search
Difference Between Vector Store and Vector Database
Vector Store
•
Typically a lightweight library or service focused on storing vectors (embeddings) and performing similarity searches.
•
Often lacks traditional database features like transactions, rich query languages, or role-based access control (RBAC).
•
Ideal for prototyping and smaller-scale applications.
•
Examples: FAISS (where you store vectors and query them by similarity, but handle persistence and scaling separately).
Vector Database
•
A full-fledged database system designed to store and query vectors.
•
Offers additional “database-like” features:
•
Distributed architecture for horizontal scaling
•
Durability and persistence (replication, backup/restore)
•
Metadata handling (schemas, filters)
•
Potential for ACID or near-ACID guarantees
•
Authentication/authorization and advanced security features
•
Built for production environments with significant scaling and large datasets.
Vector store - We can think of it as a system that lets you store vectors and retrieve them.
If we add database powers like backup and restore, distributed architecture for scaling, ACID transactions, concurrency control, and authentication, then this system becomes a vector database.
A vector database is essentially a vector store with extra database features.
Example: Vector database - Pinecone
Vector Stores in LangChain
•
Supported Stores: LangChain integrates with multiple vector stores (FAISS, Pinecone, Chroma, Qdrant, Weaviate, etc.), offering flexibility in scale, features, and deployment.
•
Common Interface: A uniform VectorStore API allows swapping one backend (e.g., FAISS) for another (e.g., Pinecone) with minimal code changes.
•
Metadata Handling: Most LangChain vector stores let you attach metadata (e.g., timestamps, authors) to each document, enabling filtered retrieval.
Chroma Vector Store
Chroma is a lightweight, open-source vector database that’s particularly developer-friendly for local development and small- to medium-scale production.
Chroma sits between a vector store and a vector database—it’s lightweight but includes some database features.
•
Tenant means user/organization/team. A tenant can create multiple databases.
•
Within one database, you can create multiple collections. Think of a collection as a table in a database.
•
Each collection can store multiple documents. A document consists of two things: an embedding vector and metadata about that vector.
