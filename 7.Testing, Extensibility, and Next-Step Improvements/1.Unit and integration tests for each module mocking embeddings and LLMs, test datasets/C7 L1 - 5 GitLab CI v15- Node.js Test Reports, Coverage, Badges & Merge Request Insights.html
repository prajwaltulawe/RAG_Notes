Gitlab CI for Node Testing and Coverage
A look at the Gitlab CI v15.0 features for Nodejs
GitLab is a popular open-source version control system that’s free to use and can be self-hosted on an intranet. GitLab offers many useful features, such as GitLab CI.
GitLab has been integrating CI/CD pipelines into the platform for a long time and has developed the so-called GitLab Flow. In this article, I won’t cover the full GitLab CI guide or explain CI/CD concepts, but will focus on how to make Node testing reports more visually appealing.
Why this topic? The main reason is that we often use nyc and mocha together to generate testing reports for Node, but this combination needs a few tweaks to integrate well with GitLab’s rich functionality. This article covers those approaches and uses a real .gitlab-ci.yml as an example.
Please note that this article is based on GitLab v15.0
Testing Report
A good testing report needs several key features.
1.
an artifact of the full report.
2.
test summary for each Pull Request or Merge Request.
3.
the change coverage for each Pull Request or Merge Request.
4.
the status of the entire pipeline, including the latest success or failure and its coverage, preferably in the form of a badge.
Report Artifacts
This is the latest pipeline report, which can be downloaded here. To enable this, we need to add an artifacts field to specify the path to export at the desired stage. For example, in the figure above, the setting would be as follows.
test_ci: script: - npm run test artifacts: paths: - coverage/
This exports everything under the coverage folder as a package.
Test Summary
To display test results in a Merge Request—including how many cases were tested, how many passed or failed, and even how long each took—you need to tell GitLab the format of the testing report and produce the results in that format.
So let’s extend the .gitlab-ci.yml example above.
test_ci: script: - npm run test artifacts: paths: - coverage/ reports: junit: - test-results.xml
In this example, we use the JUnit format for the testing report and point GitLab to the CI report path. This allows GitLab to display the correct report content and summary in each Merge Request.
Change Coverage
During code review, we all click into Changes to see what parts have been modified.
It would be more efficient if reviewers could see the test coverage of those changes right here in one place. We want to make it easy for reviewers to spot untested code.
In this image, we can instantly see that line 14 lacks test coverage, while the others are covered. It’s worth noting that even with test coverage, it doesn’t guarantee comprehensive testing—for example, boundary conditions can’t be verified here, so it still relies on the reviewer’s experience.
Then, we extend the original settings further.
test_ci: script: - npm run test artifacts: paths: - coverage/ reports: junit: - test-results.xml coverage_report: coverage_format: cobertura path: coverage/cobertura-coverage.xml
Pipeline Badges
In popular open-source projects today, users see the project’s health status right at the top of README.md. This is useful info for users and a quick check for developers.
If the pipeline status shows failure, something’s wrong. Meanwhile, the coverage badge is a great indicator of test completeness.
Fortunately, badges are a built-in GitLab feature. You can find badge URLs in GitLab settings.
Settings > CI/CD > General pipelines
There are three types: Pipeline status, Coverage report, and Latest release. Pick what you need.
Since GitLab v15.0, you can use a regular expression in re2 syntax in .gitlab-ci.yml to parse coverage numbers.
test_ci: script: - npm run test coverage: '/All files\s+\|\s+\d+\.\d+/'
This re2 syntax rule captures the floating-point number after All files as coverage. If you’re not using nyc, adjust the rule to match your output.
Detail in package.json
The example above fully implements the essential features for development. But we haven’t explained how to generate coverage reports, JUnit reports, and change coverage simultaneously.
The key is in npm run test, i.e., package.json.
{ "scripts": { "test": "nyc --reporter=html --reporter=text --reporter=cobertura mocha" } }
From these settings, this hardworking nyc generates three output types for the three features:
•
html: Serves as the full project coverage report, used when downloading artifacts.
•
text: Console output needed for badges.
•
cobertura: As discussed earlier, change coverage uses the cobertura format.
Wait, one missing? Who generates the JUnit reports? It’s mocha. But this isn’t built into mocha, so we need an extra tool.
First, install the mocha-junit-reporter package.
npm i mocha-junit-reporter --save-dev
Next, create the mocha config file, .mocharc.js.
module.exports = { reporter: "./junit-spec-reporter.js" };
In the config, we tell mocha to use another file for reporting, which is our JUnit generator.
Here’s the content of junit-spec-reporter.js.
const mocha = require("mocha"); const JUnit = require("mocha-junit-reporter"); const Spec = mocha.reporters.Spec; const Base = mocha.reporters.Base;
function JunitSpecReporter(runner, options) { Base.call(this, runner, options); this._junitReporter = new JUnit(runner, options); this._specReporter = new Spec(runner, options); return this; } JunitSpecReporter.prototype.__proto__ = Base.prototype;
module.exports = JunitSpecReporter;
Now, all required formats are generated correctly. GitLab CI will render a rich view from these outputs, letting developers handle most routine tasks on GitLab’s web interface without building locally.
Conclusion
CI/CD is a crucial software development practice. But to keep every developer engaged and confident in continuing it, they need to “see” the changes.
For engineers, seeing is believing—that’s most of us. So these rich features are essential for pipelines to be truly effective.
The full .gitlab-ci.yml, including all mentioned features, is as follows.
test_ci: script: - npm run test artifacts: paths: - coverage/ reports: junit: - test-results.xml coverage_report: coverage_format: cobertura path: coverage/cobertura-coverage.xml coverage: '/All files\s+\|\s+\d+\.\d+/'
In my experience, when a testing platform is first built, not everyone is thrilled to use it—writing tests is extra work, after all. But when the platform is rich enough, most people are willing to give it a try.
For a team just starting to establish a development process, getting buy-in is more important than anything else.
That’s why this article focuses on GitLab CI presentation and highlights CI’s role in the development process from a fresh angle.
