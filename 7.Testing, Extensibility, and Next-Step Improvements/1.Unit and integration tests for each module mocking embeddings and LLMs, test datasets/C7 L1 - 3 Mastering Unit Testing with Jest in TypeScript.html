Unit Test | Part I
You wake up in the morning, make your daily coffee, and sit down at your computer to start developing new features. You know the day is short, so you go full throttle.
At the end of the day, you did it—you developed that feature that was so hard to get out. Happy, you step out for some fresh air and return to your cave to face another challenge.
But… how do you know if that implemented logic actually works? You probably tested it by inputting data you expect and getting the result it was programmed for, but unfortunately, that’s not enough. That’s why we need to subject our code to rigorous tests and see how it reacts.
This is where unit tests come in.
But… What Are Unit Tests?
We know that implementing a solution doesn’t depend on just one function or method, but rather on different parts that, orchestrated through inputs, outputs, and flow controls, solve the problem.
Unit tests aim to test your code on a unit-by-unit basis, as the name suggests. Here, you’re not testing the complete solution, but only a specific component.
The idea is to subject that function or method to various execution scenarios, such as unexpected arguments like different values, incorrect ones, malformed, null, undefined, among others, as well as the responses it might give—from expected ones to unexpected ones and errors, among others.
There are other types of tests known as ‘End-to-End Tests’ (Pruebas End-to-End), which, as the name implies, are tests from start to finish. Here, you do test the complete solution. But that’s not within the scope of this post.
Great! Now you know what a unit test is; now we need to understand it.
How Does It Work?
Starting with the basics: just a method or function with no dependencies, only logic and its arguments. We can test it by calling the function or method, passing the arguments, and validating the returned value against an expected one.
Now, if it’s something more complex with dependencies like services, other functions, etc., we need to mock them by emulating their behavior, since we’re only interested in testing the code unit and not its dependencies. Similarly, as mentioned earlier, we pass the arguments and validate the returned value against an expected one.
Of course, it’s not just that, and it’s necessary to use packages, libraries, or assemblies depending on the language you’re using. For that, you can check this link to find the tool that fits your requirements.
Before diving into code, you should know that TypeScript will be used for the following examples along with Jest. If you’re working in another language, I recommend checking the aforementioned link and finding the tool that best suits you.
Unit Test | The Basics
We have a function that returns Hello , where value is the value we pass to the function.
This function, which has no dependencies, I’ll test with the following cases:
1.
If I pass “World” to hello (without quotes), it should return Hello World
2.
If I pass an empty string to hello, it should return Hello
3.
If I pass a 1 to hello, it should return “Only string values accepted” (“Solo acepta valores strings”)
For these tests, I’ll use 4 basic Jest functions: describe, it, and expect
•
describe: Allows grouping and describing a set of tests, which helps us build a narrative of the tests being performed. It’s important to know that these don’t execute tests and are optional.
•
it: Allows executing tests; they can be nested inside a describe or standalone. Here, the phases of each test take place.
•
expect: Allows us to pass the returned value from the tested function and compare it, throwing an error if the condition isn’t met.
The phases of the test set are:
•
prepare: Phase where we set up the test, such as expected values, spyOn for functions, etc.
•
execute: Phase where we pass the arguments (if required) and call the function to test, storing the result in a constant.
•
validate: Phase where we validate the result of the function call. Jest has various functions to help with validation.
If we run npm run test, we’ll get the following result:
> example-simple-unit-test@1.0.0 test > jest FAIL src/index.spec.ts √ should return Hello World when args is World (3 ms) √ should return Hello when args is empty (1 ms) × should return message error when args is number 1 (4 ms) ● should return message error when args is number 1 expect(received).toEqual(expected) // deep equality Expected: "Solo acepta valores strings" Received: "Hello 1" 24 | const result = hello(1 as any); // use any to force input 25 | //validate > 26 | expect(result).toEqual(expectedValue); | ^ 27 | }); 28 | //}); at Object. (index.spec.ts:26:24) Test Suites: 1 failed, 1 total Tests: 1 failed, 2 passed, 3 total Snapshots: 0 total Time: 1.812 s, estimated 2 s Ran all test suites.
If we read the console, we can see that the test in src/index.spec.ts failed, showing checkmarks for those that passed and an x for those that failed. It then indicates the validation that failed, describing what was expected and what was received, finishing with a summary of the failed Suites and Tests.
Recalling the tests we proposed, 2 out of 3 passed, but the third failed because it expected “Solo acepta valores strings” (“Only string values accepted”) when we passed the numeric value 1 as an argument, but as we see in the console, it returned Hello 1.
Although it’s a basic example, it allows us to validate that under certain conditions, the function returns what we expect. In this case, we realize there’s a missing validation so that if a number is passed, it returns the expected message.
With that in mind, we’ll modify the function since we need to validate the input and, if it’s not a string, return the message “Solo acepta valores strings” (“Only string values accepted”). NOTE (OJO): We shouldn’t modify the test—that’s the point, to realize our code has deficiencies.
We added an additional validation: if the argument type is not string, it returns the message “Solo acepta valores strings”.
If we run the test again, we’ll get:
> example-simple-unit-test@1.0.0 test > jest PASS src/index.spec.ts Hello function √ should return Hello World when args is World (2 ms) √ should return Hello when args is empty √ should return message error when args is number 1 Test Suites: 1 passed, 1 total Tests: 3 passed, 3 total Snapshots: 0 total Time: 1.825 s, estimated 2 s Ran all test suites.
Now the result is PASS.
The Relevance
This certification process allows us to increase the reliability of our code and is widely used when CI/CD is implemented, as it’s crucial that new development or modifications to existing ones keep everything working well without breaking anything with our intervention, minimizing potential failures in production.
