Contextual Metadata Filtering RAG (CMF-RAG)
How to automatically generate metadata filters to improve retriever quality in RAG
RAG (Retrieval Augmented Generation) is a pretty straightforward concept in Generative AI: given a user prompt, the system will retrieve some chunks of text that are semantically close to that prompt, and use them as context for an LLM to provide an answer.
There are multiple tweaks one can do to that, particularly on how to identify the set of chunks to retrieve: we can simply get the 10 most similar chunks, or enforce some kind of diversity, to get a broader context.
One of the tweaks that I don’t see often, and that can be very effective is Contextual Metadata Filtering RAG (CMF-RAG): first asking the LLM to categorize the prompt based on pre-determined labels, and then use that to filter the chunks on their metadata.
For example, imagine you have multiple files with information on a company, organized in folders according to their subject: financial statements, compensation policy, strategy, board meeting minutes, etc.
In “vanilla” RAG, we ask our retriever to blindly go over all those documents, trying to find relevant chunks of text. However, these chunks might seem relevant when we look at them individually, but not when we take into account the context.
Going back to our example, imagine we want to know “when will the new compensation compliance measures be implemented” in the company. Maybe one of the board meeting minutes contains a chunk saying “the new compliance measures will be implemented next month.” Just looking at the chunk, however, we can’t know if these compliance measures concern compensation or not. If this same chunk belongs to a file under “compensation policy”, however, then it’s much more likely that this fits our needs.
Traditional RAG techniques don’t address this, but if we first provide a list of the folder names to our LLM and ask it to give us which ones could be relevant to answer the question in the prompt, it would likely include “compensation policy”. This tag could then be passed on to the retriever, to fetch only chunks that came from inside that folder (using metadata).
For this approach to work, we need to:
•
provide the list of possible tags to our LLM, written exactly as they are in the metadata (this can be done programatically, to incorporate updates in the metadata);
•
reinforce the need for a structured output (JSON-like or list format);
•
use few-shot prompting, to give some examples of the expected output;
Here’s a simplified example of a pre-prompt for our previous use case, for illustration:
Given a user question, try to label it under one or more of the categories below: [ 'compensation policies', 'HR', 'board meeting minutes', 'financial statements', 'IT documentation', 'press releases' ] The idea is to identify possible subject tags for files that may contain relevant information to answer the user request. Here are a few examples: User: 'How many days off do we get every year?' Agent: '[HR]' User: 'What were the most important decisions made by the company last year?' Agent: ['press releases', 'board meeting minutes'] Make sure to answer with the list of strings only, between brackets, and no additional text. Do not invent any labels, only use those provided above.
This pre-prompt can be stored in a .txt file, and fetch the list of possible tags dynamically, to adapt to any updates in the vector database, and to make sure the values are written exactly as they are in the database.
Personally, I have used this strategy for a conversational search bar, aimed to help users find products in a retailer’s database, and had multiple chains running in parallel, to extract information such as product brand, category, characteristics, etc. This has vastly improved the results when compared to a simple retriever.
One downside, however, is that it makes two sequential LLM calls instead of one, which increases latency.
