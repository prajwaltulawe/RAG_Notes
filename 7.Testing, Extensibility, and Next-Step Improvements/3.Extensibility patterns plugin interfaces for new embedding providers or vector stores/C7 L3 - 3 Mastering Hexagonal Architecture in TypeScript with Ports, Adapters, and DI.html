Hexagonal Architecture (Ports and Adapters) in Practice with TypeScript
I’m very interested in application architecture. I believe that when applied wisely, good architectural choices help software development teams deliver with quality and confidence. One architecture that’s been getting a lot of attention lately is Hexagonal Architecture, also known as Ports and Adapters.
One of the main goals of this architecture is to decouple business code from the external world (in my interpretation, everything our code doesn’t control: databases, third-party services, transport layers, etc.).
There are plenty of materials on the subject, but I feel there’s a lack of examples on how to apply it using TypeScript. So, this post aims to bring some elements of the architecture and how they can be implemented using the language. It’s important to note that this architecture can be used in any language, but TypeScript—and particularly type checking—can make adoption and consistency easier.
The opinions and ideas here are my interpretation of both the architecture and the implementation, and nothing here should be taken as absolute truth. Many of these things are what works for me and the teams I’ve worked with.
The architecture
I think Herberto Graça’s interpretation in Ports & Adapters Architecture is fantastic. The image above (credits to Herberto) demonstrates the essence of the architecture very well: placing business rules at the center of the solution and creating interaction points with the external world.
In summary, a port represents a contract, while an adapter is a concrete implementation that fulfills the established contract.
In the TypeScript examples later on, we can identify something as an adapter or a port based on how we write the code. Ports are represented by interfaces, while adapters are the classes (or an object with a set of functions) that implement them concretely.
If you want to dive deeper, there are materials that mention terms like primary adapters (that use the system, e.g., an HTTP controller) and secondary adapters (that are used by the system, e.g., a database). However, I believe these concepts can hinder understanding. The key point is: separate business logic from the external world, regardless of what these things are called.
How TypeScript fits into this architecture
I see TypeScript as a great language for this type of architecture because its interfaces perform structural validation in type checking. In other words, if the interface defines a method like send(value: string), you just need a concrete implementation with that method and parameter to use it.
Modeling the application domain
I like to start an application by modeling the domain. I think it’s the time to think about what the application does, disregarding things like persistence and external services. Not that those things aren’t important, but having the domain well modeled, tested, and validated is the first step before starting those other integration processes.
Domain modeling consists of identifying the business problem being solved, translating it into code, and validating it. Normally, this domain will be pure and won’t be influenced by the external world at all. Persisting data
Continuing with the subscription plan example, the next step is to persist the pure information in a database and also retrieve information about existing plans.

Bonus: dependency injection
So far, we’ve seen that hexagonal architecture can be easily practiced just by creating interfaces and concrete implementations. However, when we actually run the application, we’ll need to instantiate some concrete implementations. This instantiation ends up making us aware of the external world, which goes a bit against what this architecture preaches.
