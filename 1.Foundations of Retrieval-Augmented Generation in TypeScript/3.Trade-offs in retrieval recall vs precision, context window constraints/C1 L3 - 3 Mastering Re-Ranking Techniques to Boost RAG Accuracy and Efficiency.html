98. Re-ranking Techniques in RAG: Cross-Encoders and Beyond
Your RAG system retrieves 100 documents using a vector database. The top result has a similarity score of 0.85. The 10th result has a score of 0.70.
You pass the top 10 to the LLM. But the actual best document for answering the user’s question might be the 7th one, not the 1st.
This is the re-ranking problem.
Initial retrieval (using vector search) gives you a rough ranking. But rough isn’t good enough for production. You need to re-rank those results to find the truly best matches.
Re-ranking is a second-pass ranking that improves the quality of retrieved documents.
Initial retrieval is fast but approximate. Re-ranking is slower but more accurate. You use both together: retrieve top 100 quickly with vectors, re-rank top 100 accurately with a stronger model.
This post covers re-ranking techniques, how they work, and how to implement them.
The Initial Retrieval Problem
Vector search is efficient but has limitations.
When you embed a query and documents, you’re using a symmetric model. The same embedding approach works for both. The embedding captures semantic similarity but doesn’t deeply understand the relationship between a specific query and a specific document.
Example: A user searches “How do I install Python?”
Your vector search might retrieve:
1.
“Python Installation Guide” (score: 0.92)
2.
“Setting Up Your Development Environment” (score: 0.89)
3.
“Why Python is Popular” (score: 0.85)
Ranking looks reasonable. But “Why Python is Popular” (rank 3) has almost nothing to do with installation. The algorithm just saw semantic similarity.
If the LLM only sees the top 5 results, it misses other highly relevant documents that ranked lower due to embedding limitations.
Re-ranking solves this by using a more sophisticated model on the top-k results.
What is Re-ranking?
Re-ranking is a second stage in retrieval that re-scores documents.
The process:
1.
Initial retrieval: Use vector search to get top 100 documents (fast, approximate)
2.
Re-rank: Score those 100 documents with a stronger model (slower, more accurate)
3.
Return: Top k documents from the re-ranked list
The key insight: you don’t re-rank all 1 million documents. You only re-rank the top candidates from initial retrieval. This gives you the accuracy of a strong model with the speed of fast initial retrieval.
Why does this work? Because the initial retrieval, while approximate, is good enough to narrow the problem. The truly best matches are usually in the top 100. Re-ranking refines from there.
Technique 1: Cross-Encoders
A Cross-Encoder is a neural network that takes a query and document as input and outputs a relevance score.
Unlike vector search (which embeds query and document separately), a Cross-Encoder embeds them together.
How it works:
Input: A query-document pair formatted as: “[CLS] query [SEP] document [SEP]”
Output: A relevance score (e.g., 0–1 or 1–5)
The model learns to understand the interaction between query and document directly.
Example:
Query: “How do I install Python?” Document: “Python Installation Guide - Step by step instructions…”
The Cross-Encoder jointly processes the query and document, understanding their relationship. It produces a score like 0.95 (highly relevant).
Same query, different document: Document: “Why Python is Popular - Python’s advantages…”
The Cross-Encoder produces a score like 0.62 (less relevant).
Why it’s better:
Cross-Encoders understand query-document interactions. They can capture that “install” in the query is highly relevant to “installation guide” in the document. They understand context and nuance.
Vector embeddings can’t do this level of understanding because they embed independently.
Trade-off:
Cross-Encoders are slower. Scoring a document with a Cross-Encoder requires a forward pass through the model. With vectors, you just do a dot product.
For 100 documents, Cross-Encoder takes 100ms. Vector similarity takes 1ms.
So you don’t use Cross-Encoders for initial retrieval. But for re-ranking 100 documents? 100ms is acceptable.
Popular Cross-Encoder Models:
•
cross-encoder/ms-marco-MiniLM-L-6-v2: Fast, good quality
•
cross-encoder/ms-marco-MiniLM-L-12-v2: Better quality, slower
•
cross-encoder/qnli-distilroberta-base: Good for general relevance
•
cross-encoder/stsb-roberta-large: Semantic textual similarity
# Cross-Encoder re-ranking from sentence_transformers import CrossEncoder class CrossEncoderReranker: def __init__(self, model_name='cross-encoder/ms-marco-MiniLM-L-6-v2'): self.model = CrossEncoder(model_name) def rerank(self, query, documents, top_k=10): """Re-rank documents using a Cross-Encoder model""" # Prepare query-document pairs pairs = [[query, doc] for doc in documents] # Score all pairs scores = self.model.predict(pairs) # Create ranking with scores ranked = list(zip(documents, scores)) ranked.sort(key=lambda x: x[1], reverse=True) # Return top k return ranked[:top_k] # Example usage reranker = CrossEncoderReranker() query = "How do I install Python?" documents = [ "Python Installation Guide - Step by step instructions for Windows, Mac, Linux", "Why Python is Popular - The advantages of Python for development", "Getting Started with Python - Your first program", "Python Virtual Environments - Managing dependencies", "Advanced Python Features - Decorators and metaclasses", "Python for Data Science - NumPy and Pandas tutorial" ] results = reranker.rerank(query, documents, top_k=5) for i, (doc, score) in enumerate(results): print(f"{i+1}. Score: {score:.3f}") print(f" {doc[:60]}...") print()
Technique 2: ColBERT (Contextualized Late Interaction)
ColBERT takes a different approach. Instead of one Cross-Encoder score, it uses fine-grained interactions.
How it works:
1.
Embed the query into multiple token embeddings (not one embedding, but one per token)
2.
Embed each document into multiple token embeddings
3.
For each query token, find the maximum similarity to any document token
4.
Sum these maximum similarities
The key insight: relevance comes from matching tokens in context, not overall similarity.
Example:
Query: “How install Python” (embeddings for each word) Document: “Python Installation Guide - Install Python step by step”
ColBERT finds:
•
“install” token in query matches “Install” token in document: similarity 0.95
•
“Python” token in query matches “Python” tokens in document: similarity 0.98
•
“How” token in query doesn’t match well: similarity 0.30
Final score is a sum of max similarities: 0.95 + 0.98 + 0.30 = 2.23
Why it’s better:
ColBERT catches detailed matches. If a document contains all the exact words from the query (in context), ColBERT gives a high score. Vector similarity might miss this.
ColBERT is faster than Cross-Encoders because it’s more efficient. You can pre-compute document embeddings once, then only compute query embeddings per request.
Trade-off:
ColBERT requires more memory (storing token-level embeddings). It’s more complex than both vector search and Cross-Encoders.
But for production systems, it’s often the best balance of speed and quality.
# ColBERT re-ranking (simplified version) import numpy as np from sentence_transformers import SentenceTransformer class ColBERTReranker: def __init__(self, model_name='sentence-transformers/all-MiniLM-L6-v2'): self.model = SentenceTransformer(model_name) def _get_token_embeddings(self, text): """Get embeddings for each token in text""" # Simplified: split by space and embed each token # In practice, use proper tokenization tokens = text.split() embeddings = [] for token in tokens: # Embed individual token emb = self.model.encode(token, convert_to_tensor=False) embeddings.append(emb) return tokens, np.array(embeddings) def rerank(self, query, documents, top_k=10): """Re-rank using ColBERT-style token interaction""" query_tokens, query_embs = self._get_token_embeddings(query) scored = [] for doc in documents: doc_tokens, doc_embs = self._get_token_embeddings(doc) # For each query token, find max similarity to doc tokens score = 0 for q_emb in query_embs: # Cosine similarities between query token and all doc tokens similarities = [] for d_emb in doc_embs: sim = np.dot(q_emb, d_emb) / \ (np.linalg.norm(q_emb) * np.linalg.norm(d_emb) + 1e-10) similarities.append(sim) # Take max similarity max_sim = max(similarities) if similarities else 0 score += max_sim scored.append((doc, score)) # Sort by score scored.sort(key=lambda x: x[1], reverse=True) return scored[:top_k] # Example usage reranker = ColBERTReranker() query = "install Python" documents = [ "Python Installation Guide - Install Python step by step", "Why Python is Popular", "Getting Started with Python - Your first program", "Python for Data Science", ] results = reranker.rerank(query, documents, top_k=3) for i, (doc, score) in enumerate(results): print(f"{i+1}. Score: {score:.3f}") print(f" {doc[:50]}...")
Technique 3: Learned-to-Rank (LTR)
A more sophisticated approach: train a learning-to-rank model.
The idea: instead of using a pre-trained model, train a model specifically for your domain.
How it works:
1.
Collect query-document pairs with relevance labels (good match: 1, bad match: 0)
2.
For each pair, compute features (vector similarity, BM25 score, Cross-Encoder score, etc.)
3.
Train a model (gradient boosted trees, neural network) to predict relevance from features
4.
At inference, score documents using the trained model
Features you might use:
•
Vector similarity score
•
BM25 keyword matching score
•
Document length
•
Query-document token overlap
•
Cross-Encoder score
•
Domain-specific features (e.g., document quality, freshness)
Why it’s better:
LTR learns what matters for your specific domain. A query about “Python installation” needs different ranking signals than a query about “machine learning papers.”
With LTR, you can combine signals intelligently. Maybe vector similarity accounts for 30% of the score, BM25 for 20%, and Cross-Encoder for 50%.
Trade-off:
LTR requires labeled training data. You need to collect hundreds or thousands of query-document pairs with relevance judgments.
But in production systems, this is worth it. You get domain-specific ranking.
# Learning-to-Rank re-ranking (simplified) import numpy as np from sklearn.ensemble import GradientBoostingRanker from scipy.sparse import csr_matrix class LTRReranker: def __init__(self): self.model = GradientBoostingRanker() self.is_trained = False def extract_features(self, query, document): """Extract features for a query-document pair""" features = [] # Feature 1: Query-document token overlap q_tokens = set(query.lower().split()) d_tokens = set(document.lower().split()) overlap = len(q_tokens &amp; d_tokens) / len(q_tokens | d_tokens) features.append(overlap) # Feature 2: Document length doc_length = len(document.split()) features.append(np.log(doc_length + 1)) # Feature 3: Query term frequency in document query_terms_in_doc = sum(1 for term in q_tokens if term in document.lower()) features.append(query_terms_in_doc) # Feature 4: Position of first query match for i, word in enumerate(document.lower().split()): if word in q_tokens: features.append(1.0 / (i + 1)) # Earlier is better break else: features.append(0) return np.array(features) def train(self, queries, documents, labels): """Train LTR model on labeled data""" X = [] y = [] for query, doc, label in zip(queries, documents, labels): features = self.extract_features(query, doc) X.append(features) y.append(label) X = np.array(X) y = np.array(y) # Train gradient boosting ranker self.model.fit(X, y) self.is_trained = True def rerank(self, query, documents, top_k=10): """Re-rank documents using trained LTR model""" if not self.is_trained: raise ValueError("Model not trained. Call train() first.") scored = [] for doc in documents: features = self.extract_features(query, doc).reshape(1, -1) score = self.model.predict(features)[0] scored.append((doc, score)) scored.sort(key=lambda x: x[1], reverse=True) return scored[:top_k] # Example usage (would need real training data) reranker = LTRReranker() # In practice, you'd collect many query-document pairs with labels training_queries = ["install Python", "Python tutorial"] training_docs = ["Python Installation Guide", "Getting Started with Python"] training_labels = [1, 1] # 1 = relevant, 0 = not relevant reranker.train(training_queries, training_docs, training_labels) # Now use for re-ranking query = "install Python" documents = [ "Why Python is Popular", "Python Installation Guide", "Python for Data Science" ] results = reranker.rerank(query, documents, top_k=2) for i, (doc, score) in enumerate(results): print(f"{i+1}. Score: {score:.3f}") print(f" {doc}")

Real-World Pipeline: Vector Search + Re-ranking
Here’s what production systems actually do:
# Production RAG retrieval pipeline class RAGRetriever: def __init__(self, vector_db, reranker): self.vector_db = vector_db self.reranker = reranker def retrieve(self, query, k=10, initial_k=100): """ Retrieve documents using vector search + re-ranking Args: query: user query k: number of final results initial_k: number of candidates for re-ranking """ # Step 1: Vector search (fast, approximate) initial_results = self.vector_db.search(query, k=initial_k) # Returns: [(doc_id, doc_text, vector_score), ...] # Step 2: Extract documents for re-ranking documents = [doc_text for _, doc_text, _ in initial_results] # Step 3: Re-rank (slower but accurate) reranked = self.reranker.rerank(query, documents, top_k=k) # Returns: [(doc_text, rerank_score), ...] # Step 4: Return final results final_results = [] for i, (doc_text, rerank_score) in enumerate(reranked): final_results.append({ 'rank': i + 1, 'text': doc_text, 'relevance_score': rerank_score }) return final_results # Usage pipeline = RAGRetriever(vector_db=my_vector_db, reranker=my_reranker) results = pipeline.retrieve("How do I install Python?", k=10, initial_k=100) for result in results: print(f"Rank {result['rank']}: {result['relevance_score']:.3f}") print(f" {result['text'][:80]}...")
When to Use Re-ranking
Use re-ranking if:
•
Retrieval quality is critical (you measure it and want to improve)
•
You can afford the latency (re-ranking adds 50–500ms)
•
Your documents are complex or ambiguous
•
Users expect high-quality results
Don’t use re-ranking if:
•
Speed is critical (every millisecond matters)
•
Your dataset is small (vector search is already good)
•
You’re just prototyping
•
Your budget doesn’t allow for model inference
In production systems:
Most use re-ranking. The quality improvement is worth the extra latency. Users don’t notice 100ms extra if they get better results.
Implementation Considerations
Batching:
Don’t re-rank one document at a time. Batch documents together. Re-ranking 100 documents is faster per-document than re-ranking 10 separately.
# Better: batch scores = cross_encoder.predict([[query, doc] for doc in documents]) # Worse: loop scores = [] for doc in documents: score = cross_encoder.predict([[query, doc]])[0] scores.append(score)
Caching:
Pre-compute document embeddings (for ColBERT). Don’t re-embed the same document each time.
# Cache embeddings doc_embeddings = {} for doc_id, doc_text in documents.items(): doc_embeddings[doc_id] = colbert_model.encode(doc_text) # At inference, only compute query embedding query_emb = colbert_model.encode(query) # Then do efficient token matching with cached doc embeddings
Thresholding:
Set a minimum relevance score. If a document scores below 0.3, it’s probably not relevant.
# Filter low-scoring results results = reranker.rerank(query, documents) filtered = [(doc, score) for doc, score in results if score > 0.3]
Pitfalls to Avoid
Re-ranking everything:
Don’t re-rank all 1 million documents. Re-rank the top 100 from vector search. The cost isn’t worth it.
Ignoring initial retrieval quality:
If your initial retrieval is poor, re-ranking won’t save you. The truly relevant document might be ranked 500th. No re-ranker can fix that.
Over-optimizing for metrics:
You can make a metric (like MRR@10) go up with re-ranking, but it might not correlate with actual user satisfaction. Measure what matters.
Cold start:
LTR models need training data. For new domains, start with pre-trained Cross-Encoders or ColBERT, then switch to LTR once you have labeled data.
Conclusion
Re-ranking is a second-pass ranking that improves retrieval quality.
Initial retrieval (vector search) is fast and approximate. Re-ranking is slower but accurate. You combine both: retrieve top 100 quickly, re-rank carefully.
Cross-Encoders are the simplest and most effective for most use cases. They’re pre-trained and don’t require domain expertise.
ColBERT is faster and works well for token-matching problems. It’s good for technical documents where exact terms matter.
LTR is most powerful but requires training data. Use it when quality matters and you have resources to collect labels.
