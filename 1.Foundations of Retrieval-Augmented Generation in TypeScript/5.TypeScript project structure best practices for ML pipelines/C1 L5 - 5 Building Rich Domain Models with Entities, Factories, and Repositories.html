What I Learned from Non-Anemic Domain Models?
If I had to cite a moment when EVERYTHING made sense, it was understanding a post about the Anemic Domain Model by Martin Fowler. Notice that I said “understanding” and not “reading” because the time between my first encounter with the concept and when I actually understood it wasn’t very short.
Understanding the importance of having non-anemic domains helped me understand DDD much better and even made TDD viable. During my learning journey, I had some lessons, and my goal is to share them with you in this post.
😶‍🌫️ Investing in the domain isn’t just about stuffing entities with behaviors
Stuffing entities with behaviors is just object-oriented programming; the real key is what you put inside the entities and what other techniques you can use in your domain to encapsulate the business rules within it.
The first pattern I applied in my code after starting to understand Martin Fowler’s article was the Factory Pattern. In a nutshell, a factory is meant to “manufacture” objects. So, if I need to generate a new order in an online store, my Order factory sits in the application’s domain layer, and it contains all the business rules for creating the order—for example: the customer must not be in debt, the product must be in stock, etc.
🧘🏽‍♀️ Life is already complicated enough—keep your code simple
What I’ve seen in the careers of most developers I’ve worked with is that there’s a professional evolution phase where we start wanting to make everything more complex than it really is. We think that writing hard-to-understand code is a sign of experience, and that’s where people get lost.
A personal motto I always follow is that my code should be so simple that it reads like a story to whoever is reading it. For that to work well, I need to maintain ubiquitous language and heavily invest in modeling and developing my domain.
👌🏽 The domain can use repository interfaces
When we learn layered architecture or DDD, in the domain project we have two main types of classes: entities and repository interfaces, right? Well, I had never truly understood why, technically, the repository interface had to be in the domain since the repository was used in the application layer.
And the point is exactly that: the repository is used in the other layers, but nothing stops me from using the interface in the domain. Taking the factory example I mentioned earlier, checking the availability of the requested product in stock will likely be retrieved from a data source, and the repository interface can be used in the factory to get that information and apply the proper validations.
✅ TDD becomes easier because we know where the code will be implemented
I’ve always understood the TDD concept but never found it viable—I didn’t get how I could write a test and implement validations before any code even existed. The thing is, when the domain is well-modeled, it’s much easier to know where a piece of code will go in the future, and with that, I can create the test beforehand.
Once again using the factory example, if I need to test order creation behavior, all my tests should be run against the factory. If I need to test order closing behavior, since the domain modeling has already defined that the behavior belongs to the Pedido value object, then my test code will target the Pedido entity’s behavior.
🤹🏽‍♀️ The application layer is just orchestration
Orchestration is the “art” of calling each function at the moment it needs to be executed and having action plans in case the function doesn’t succeed—basically, making everything work without dropping the ball lol. Here’s a pseudo-algorithm of what the application layer should look like for the order creation feature.
1.
Get the properties needed to create the order;
2.
Call the order factory;
3.
Check if any error occurred and handle it accordingly if so;
4.
Persist the order in the database;
5.
Send an email to the customer informing them that the order has been created;
Notice there’s no business logic? Exactly—because my business rules are where they belong: in the domain.
The lessons shared above, even though they span various scopes, have two things in common: ensuring code readability and quality. Code that’s easier to understand is easier to maintain, modify, and extend. Properly tested code gives us confidence for maintenance, changes, and extensions 💡
So simple yet so hard at the same time! I don’t think anything I wrote above is that innovative—you’ve probably already read about it in other blogs, forums, or articles. But if I can give you one more tip: do the basics well.
