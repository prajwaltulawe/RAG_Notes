Testing TypeScript interfaces with jest-mock-extended
Our company recently transitioned our codebase from mocha to Jest for numerous reasons which are all well documented, most notably, standardisation. Previously we were using a mix of libraries to test our sizable (300k+LOC) node based React app - mocha, chai, enzyme, testdouble.js, ts-mockito as well as some of our own wrappers around these libraries. One of great things about Jest is that it brings together various aspects that these libraries provide into one consistent library. Just in the conversion itself I found out that there were about 10 different ways to do to.eq() in chai!
We did find that we were still yearning for some of the features provided by libraries like testdouble / ts-mockito however. This sentiment has been echoed various times in the community, and thus far it seems that most people are happy with roll your own, half baked solutions. I decided to implement a library to help with the need for this boilerplate with a goal of providng full type safety wtih TypeScript whilst keeping a jest like API - .
The Problem
If you want to use proper dependency injection in Jest, you would need to use jest.mock() to mock out the class, or you would have to roll your on implementation using jest.fn().mockImplementation({}), returning a class like structure. Even then, TypeScript support is patchy for classes and pretty much non-existent for interfaces. Yes, spys can achieve the same functionality in some cases, but sometimes it does not feel like the right tool for the job.
The Solution
jest-mock-extended provides a few helpers that make the job of mocking anything Typescript based much easier.
A simple example where we mock an TS interface which is a dependency of a class:
import { mock } from 'jest-mock-extended';
interface Device { turnOff: () => void; turnOn: () => void; getState: () => DeviceState; getProtocol: () => Protocol; } class DeviceScreen { private readonly device: Device; constructor(device: Device) { this.device = device; } onButtonClick = () => { this.device.getState() === DeviceState.ON ? this.device.turnOff() : this.device.turnOn(); } }
describe('DeviceScreen test', () => { test('calls turn on when device is off', () => { const mockDevice = mock(); const deviceScreen = new DeviceScreen(mockDevice); mockDevice.getState.mockReturnValue(DeviceState.OFF); deviceScreen.onButtonClick(); expect(mockDevice.turnOn).toHaveBeenCalled(); }); });
Argument Specific Expectations
In some situations, you want specific return values for a set of arguments -another feature that is lacking in Jest despite there being quite a bit of demand for. You could use jest-when to do this, but I prefer a more jest like API which is discussed in the above github issue. jest-mock-extended provides a calledWith() extension available to both mock objects returned from mock() and also via calledWithFn() which is a direct replacement for jest.fn()
interface Tree { getNode:(id number) => TreeNode; }
describe('TreeComponenttest', () => { test('calls turn on when device is off', () => { const mockTree = mock(); mockTree.calledWith(1).mockReturnValue(new TreeNode('Australia')); mockTree.calledWith(2).mockReturnValue(new TreeNode('New Zealand'));
const comp = new TreeComponent(mockTree);
expect(comp.getName(1)).toBe('Australia'); }); });
Argument types provided to calledWith() must match the same arguments that the method signature defines.
jest-mock-extended provides a rich set of matchers which allow for power expectations to be defined. Some examples:
mockTree.get.calledWith(anyNumber()).mockReturnValue(new TreeNode('New Zealand'));
mockProvider.createCar.calledWith(isA(Car)).mockReturnValue(new Car()) filterMock.filter.calledWith( containsKey('frog')).mockReturnValue(['amphibian'])
Matchers work with the built in Jest toBeCalledWith verifier too
expect(obj.fn).toBeCalledWith(1, 2 anyString());
Check out the documentation on github for more details.
