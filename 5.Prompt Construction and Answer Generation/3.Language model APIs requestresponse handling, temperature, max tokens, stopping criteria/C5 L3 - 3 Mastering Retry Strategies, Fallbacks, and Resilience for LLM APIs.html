Error Handling & Retries: Making LLM Calls Reliable
Series: LangChain Mastery | Post: #4 of 46 Phase: 0 - LLMs as HTTP Services | Section: 0.4 **Level:**Intermediate | Reading Time: ~9 min
Your LLM app works perfectly in development. You test it a hundred times, it never fails. You deploy it.
Three days later, a user tweets that it’s broken.
You check the logs. 429 Too Many Requests. The API rate limited you, your app threw an unhandled exception, and the user got a crash screen instead of a response.
This is not an edge case. LLM APIs fail regularly - rate limits, transient server errors, timeouts, network blips. In production, “it works when I test it” is not good enough. You need a layer between your application and the API that handles failure gracefully, retries intelligently, and degrades gracefully when things go really wrong.
That’s what this post is about.
The Types of Errors You’ll Actually Encounter
Before you can handle errors well, you need to know what you’re dealing with. LLM API errors fall into a few clear categories, and how you respond to each one is different.
4xx Client Errors - Your fault
These errors mean something is wrong with the request you sent. Retrying the same request will not help.
How to handle: Log the error with full request details, surface a meaningful message to the user, and do not retry. Fix the root cause in your code.
429 Rate Limit - Too many requests
This is the most common error in production and the one most developers handle poorly (or not at all).
{ "error": { "message": "Rate limit reached for gpt-4o in organization org-xxx. Limit: 500 RPM.", "type": "requests", "code": "rate_limit_exceeded" } }
Rate limits come in two flavors: RPM (requests per minute) and TPM (tokens per minute). You can hit either one. The response often includes a Retry-After header telling you how many seconds to wait.
How to handle: Retry with exponential backoff. This error is transient - wait a bit and try again.
5xx Server Errors - Their fault
These mean something went wrong on the API provider’s side. They’re transient and usually resolve within seconds to minutes.
How to handle: Retry with exponential backoff and jitter. These almost always resolve on their own.
Timeout Errors - Network/latency issues
These aren’t HTTP status codes - they’re exceptions thrown by your HTTP client when the connection or response takes too long.
•
Connection timeout: Can’t establish a connection to the API server
•
Read timeout: Connected, but no data received within the timeout window
How to handle: Retry with backoff. For streaming, be careful - you may have already sent partial content to the user.
Exponential Backoff & Jitter Explained
When you get a transient error, the naive approach is to retry immediately. Don’t do this. If the API is rate limiting you or experiencing high load, hammering it with instant retries makes the problem worse - for you and everyone else.
Exponential backoff means waiting progressively longer between each retry attempt:
Attempt 1 fails → wait 1s → retry Attempt 2 fails → wait 2s → retry Attempt 3 fails → wait 4s → retry Attempt 4 fails → wait 8s → retry Attempt 5 fails → give up
Each wait doubles. This gives the API time to recover while still being reasonably aggressive about retrying.
But there’s a problem: if you have 1,000 clients all doing the same exponential backoff starting at the same time, they all retry at exactly the same moments. You create synchronized “thundering herd” waves of traffic.
Jitter fixes this by adding randomness to the wait time:
import random import time def backoff_with_jitter(attempt: int, base_delay: float = 1.0, max_delay: float = 60.0) -> float: """ Full jitter strategy: wait a random amount between 0 and the exponential cap. This spreads retries across the time window and prevents thundering herds. """ exponential_cap = min(base_delay * (2 ** attempt), max_delay) return random.uniform(0, exponential_cap) # Example wait times across 5 attempts (randomized each run): for attempt in range(5): wait = backoff_with_jitter(attempt) print(f"Attempt {attempt + 1} failed → wait {wait:.2f}s") # Output (example): # Attempt 1 failed → wait 0.43s # Attempt 2 failed → wait 1.87s # Attempt 3 failed → wait 3.12s # Attempt 4 failed → wait 9.76s # Attempt 5 failed → wait 22.41s
With jitter, your retries are spread across a time window instead of synchronized, which is much friendlier to the API and more reliable for you.
Building a Reusable Retry Wrapper
Now let’s put this into a production-ready wrapper you can drop into any project. The goal is a single function that handles all the retry logic so the rest of your code doesn’t have to think about it:
import requests import json import os import time import random from typing import Optional # Errors worth retrying RETRYABLE_STATUS_CODES = {429, 500, 502, 503, 504} RETRYABLE_EXCEPTIONS = ( requests.exceptions.Timeout, requests.exceptions.ConnectionError, ) def call_with_retry( messages: list, model: str = "gpt-4o", max_tokens: int = 500, temperature: float = 0.7, max_retries: int = 4, base_delay: float = 1.0, max_delay: float = 60.0, ) -> dict: """ Call the OpenAI API with automatic retry on transient errors. Raises immediately on non-retryable errors. Returns the full response dict on success. """
last_exception = None for attempt in range(max_retries + 1): # +1 for the initial attempt try: response = requests.post( "https://api.openai.com/v1/chat/completions", headers={ "Content-Type": "application/json", "Authorization": f"Bearer {os.environ['OPENAI_API_KEY']}" }, json={ "model": model, "messages": messages, "max_tokens": max_tokens, "temperature": temperature, }, timeout=(10, 30) # (connect timeout, read timeout) ) # Non-retryable client errors - fail immediately if response.status_code in {400, 401, 403, 404, 422}: error_data = response.json().get("error", {}) raise ValueError( f"Non-retryable API error {response.status_code}: " f"{error_data.get('message', 'Unknown error')}" ) # Retryable server/rate-limit errors if response.status_code in RETRYABLE_STATUS_CODES: # Respect Retry-After header if present retry_after = response.headers.get("Retry-After") if retry_after: wait = float(retry_after) else: wait = backoff_with_jitter(attempt, base_delay, max_delay) print(f"[Attempt {attempt + 1}] Status {response.status_code} " f"— retrying in {wait:.2f}s...") time.sleep(wait) last_exception = requests.exceptions.HTTPError(response=response) continue # Success response.raise_for_status() return response.json() except RETRYABLE_EXCEPTIONS as e: if attempt == max_retries: raise # Out of retries - propagate the exception wait = backoff_with_jitter(attempt, base_delay, max_delay) print(f"[Attempt {attempt + 1}] {type(e).__name__} " f"— retrying in {wait:.2f}s...") time.sleep(wait) last_exception = e # All retries exhausted raise RuntimeError( f"API call failed after {max_retries + 1} attempts. " f"Last error: {last_exception}" ) def backoff_with_jitter(attempt: int, base_delay: float, max_delay: float) -> float: exponential_cap = min(base_delay * (2 ** attempt), max_delay) return random.uniform(0, exponential_cap) # Usage - looks just like a normal API call messages = [ {"role": "user", "content": "What is the boiling point of water?"} ] try: result = call_with_retry(messages, model="gpt-4o", max_retries=4) print(result["choices"][0]["message"]["content"]) except ValueError as e: print(f"Request error (fix your code): {e}") except RuntimeError as e: print(f"API unavailable after retries: {e}")
Key design decisions in this wrapper:
•
Distinguishes retryable from non-retryable errors - a 401 should never be retried; a 503 should always be retried
•
Respects Retry-After headers - when the API tells you exactly how long to wait, trust it
•
Separates exception types - network errors and HTTP errors are handled in the right places
•
Propagates errors cleanly - callers get ValueError for bad requests and RuntimeError for exhausted retries, so they can handle each appropriately
Fallback Strategies: When Retries Aren’t Enough
Sometimes the primary model is down or rate-limited beyond recovery. Instead of failing the user, fall back to an alternative.
Model fallback
FALLBACK_CHAIN = ["gpt-4o", "gpt-4o-mini", "gpt-3.5-turbo"] def call_with_fallback(messages: list, max_tokens: int = 500) -> dict: """ Try each model in the fallback chain until one succeeds. """ last_error = None for model in FALLBACK_CHAIN: try: print(f"Trying model: {model}") result = call_with_retry( messages=messages, model=model, max_tokens=max_tokens, max_retries=2 # Fewer retries per model so we fail fast ) if model != FALLBACK_CHAIN[0]: print(f"[Fallback] Used {model} instead of primary model") return result except RuntimeError as e: print(f"Model {model} failed: {e}") last_error = e continue except ValueError: raise # Non-retryable error - don't try other models raise RuntimeError( f"All models in fallback chain failed. Last error: {last_error}" )
Graceful degradation
When the entire API is unavailable and you can’t serve a live response, give the user something useful instead of a crash:
CANNED_RESPONSES = { "default": ( "I'm having trouble connecting right now. " "Please try again in a moment." ), "search": ( "Search is temporarily unavailable. " "Please check back shortly." ), } def call_with_graceful_degradation( messages: list, fallback_key: str = "default", model: str = "gpt-4o" ) -> str: """ Returns the model response if available, or a canned response on failure. Never raises - always returns something useful to the caller. """ try: result = call_with_fallback(messages) return result["choices"][0]["message"]["content"] except Exception as e: print(f"[Degraded mode] All attempts failed: {e}") return CANNED_RESPONSES.get(fallback_key, CANNED_RESPONSES["default"])
Graceful degradation is the last line of defense. The user gets a clear, friendly message instead of a 500 error page. Your support team doesn’t get flooded. And your monitoring catches the real issue.
The Circuit Breaker Pattern
Retries and fallbacks handle individual request failures. The circuit breaker handles a different problem: what happens when the API is down for 10 minutes and every request in your system is spending 30 seconds retrying before failing?
You’re burning resources, your users are waiting unnecessarily, and the downstream API can’t recover because it’s being hammered.
A circuit breaker tracks failures over time and “opens” the circuit when failures exceed a threshold - immediately rejecting requests instead of attempting them, giving the downstream service time to recover.
import time from enum import Enum class CircuitState(Enum): CLOSED = "closed" # Normal operation - requests flow through OPEN = "open" # Failing - requests rejected immediately HALF_OPEN = "half_open" # Testing recovery - one request allowed through class CircuitBreaker: def __init__( self,
failure_threshold: int = 5, # Failures before opening recovery_timeout: float = 60.0, # Seconds before trying again success_threshold: int = 2, # Successes to close from half-open ): self.failure_threshold = failure_threshold self.recovery_timeout = recovery_timeout self.success_threshold = success_threshold self.state = CircuitState.CLOSED self.failure_count = 0 self.success_count = 0 self.last_failure_time: Optional[float] = None def call(self, func, *args, **kwargs): if self.state == CircuitState.OPEN: # Check if recovery timeout has elapsed if time.time() - self.last_failure_time >= self.recovery_timeout: print("[Circuit Breaker] Half-open - testing recovery...") self.state = CircuitState.HALF_OPEN else: raise RuntimeError( "[Circuit Breaker] Circuit is OPEN - request rejected. " f"Retry in {self.recovery_timeout - (time.time() - self.last_failure_time):.0f}s" ) try: result = func(*args, **kwargs) self._on_success() return result except Exception as e: self._on_failure() raise def _on_success(self): if self.state == CircuitState.HALF_OPEN: self.success_count += 1 if self.success_count >= self.success_threshold: print("[Circuit Breaker] Closing circuit - service recovered") self.state = CircuitState.CLOSED self.failure_count = 0 self.success_count = 0 else: self.failure_count = 0 # Reset on success in closed state def _on_failure(self): self.failure_count += 1 self.last_failure_time = time.time() self.success_count = 0 if self.failure_count >= self.failure_threshold: if self.state != CircuitState.OPEN: print(f"[Circuit Breaker] Opening circuit after " f"{self.failure_count} failures") self.state = CircuitState.OPEN # Usage breaker = CircuitBreaker(failure_threshold=5, recovery_timeout=60.0) def make_llm_call(messages): return call_with_retry(messages, max_retries=2) try: result = breaker.call(make_llm_call, messages) print(result["choices"][0]["message"]["content"]) except RuntimeError as e: if "Circuit is OPEN" in str(e): # Circuit is open - serve from cache or return degraded response print("Service temporarily unavailable. Serving cached response.") else: print(f"Request failed: {e}")
The three states work like this:
CLOSED ──(5 failures)──► OPEN ──(60s timeout)──► HALF_OPEN ▲ │ └──────────────(2 successes)────────────────────────┘
In CLOSED state, all requests go through normally. After 5 consecutive failures, the circuit OPENS and all requests are immediately rejected. After 60 seconds, it enters HALF_OPEN - one request is allowed through to test recovery. If it succeeds twice, the circuit CLOSES again.
Putting It All Together
Here’s the full reliability stack, layered:
Your App ↓ Circuit Breaker ← Stops requests when service is down ↓ Graceful Degradation ← Returns fallback if everything fails ↓ Model Fallback ← Tries alternative models ↓ Retry + Backoff ← Handles transient errors per attempt ↓ LLM API
You don’t need all of these for every application. A simple side project might just need a retry wrapper. A high-traffic production API needs the full stack.
The key is to build each layer once, make it reusable, and compose them. That’s exactly what LangChain does internally - and now you understand what’s underneath when it does.
