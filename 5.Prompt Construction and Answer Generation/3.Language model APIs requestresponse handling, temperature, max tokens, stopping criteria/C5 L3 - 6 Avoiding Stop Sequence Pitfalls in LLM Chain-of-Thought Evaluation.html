I Changed One String, and My Model’s Score Dropped 70 Points
Understanding LLM evaluation by experimenting with different stop sequences
Qwen2.5–3B-Instruct on 40 factual questions: 70% accuracy.
Same model, same questions, same prompt, same decoding. One config change: add " " as the stop sequence.
New score: almost 0%.
I stared at this for a while before I believed it. The model didn’t get dumber. I just told it to stop talking at a different point, and the entire benchmark collapsed.
This is Part 1 of series of exploration and learnings where I investigate how “plumbing knobs” in LLM evaluation harnesses silently move benchmark scores. In this post, I focus on the stop sequence: the string that tells the model when to stop generating.
Most benchmarking setups treat stop sequences as a fixed implementation detail. You pick a stop string and move on. I wanted to find out whether that choice actually matters.
Spoiler: it does. A lot.
Why I Ran This Experiment*
I had been running evaluations on open-source instruct models and noticed something odd. Depending on which evaluation harness I used, the same model would score very differently on similar tasks. Not by a point or two. By double digits.
I started digging into the configs and realized that different harnesses make different choices about stop sequences. Some use a newline. Some use triple-hash. Some use nothing. Nobody seemed to think this mattered much.
I wanted to test that assumption directly, so I designed an experiment that isolates the stop sequence as the only variable while holding everything else constant.
The Setup
I kept things deliberately simple: two models, one dataset, one prompt template, and five stop sequence configurations. Nothing else changes between runs.
•
Models: Qwen2.5–3B-Instruct and Mistral-7B-Instruct-v0.2
•
Dataset: 40 factual QA questions with unambiguous ground-truth answers. Things like “What is the capital of France?” and “What is the chemical symbol for gold?” Simple enough that any instruct model should get most of them right.
•
Prompt: Chain-of-thought. The system message says: “Think step by step, then give your final answer on a new line starting with Answer:”. This produces outputs of 50 to 150 tokens, where the model reasons across multiple lines before writing its final answer.
•
Decoding: Greedy. No sampling, no randomness. Completely deterministic.
•
Token budget: 512. Generous enough that it never becomes the limiting factor.
The only variable: the stop sequence. I tested five configurations: no stop sequence, " ", `"
“, ”###", and "
"`.
One important note about the prompt choice. In an earlier version of this experiment, I used a short-answer prompt that told the model to respond in one word. The model answered in 2 to 3 tokens every time, stopped on its own, and no stop sequence ever had a chance to fire. Every configuration produced identical results. Flat lines across the board. I learned nothing.
The chain-of-thought format is what makes this experiment work. The model produces multi-line outputs, which gives the stop sequences something to actually cut into.
Accuracy is measured as question-level exact match against the gold answer (strict string matching).
What Happened
The newline stop destroyed both models.
Qwen went from 0.70 strict accuracy with no stop sequence down to effectively zero with the newline stop. Mistral dropped from 0.35 to about 0.075. For Qwen, that is a 70 percentage point swing from changing one string in the harness config.
The double-newline stop was almost as bad. Both models lost most of their accuracy.
Meanwhile, "###" and triple-newline behaved identically to having no stop sequence at all. The scores were the same, the output lengths were the same. These stops simply never fired, because models don’t spontaneously generate those sequences during chain-of-thought reasoning.
The mean output length tells the mechanical story. With newline or double-newline, outputs averaged around 30 tokens. With no stop, triple-hash, or triple-newline, outputs averaged 80 to 125 tokens. The newline stops are cutting off generation after the first line of reasoning, long before the model reaches its Answer: line.
One thing that surprised me: the Answer-Missing Rate was basically zero across all configurations. The parser always found something to score. It just found the wrong thing. Instead of extracting “Paris” from the Answer: line, it was pulling a fragment of truncated reasoning text and trying to match that against the gold answer. That never works.
Why the Newline Stop Is So Destructive
When I looked at the raw outputs, the mechanism became clear.
With no stop sequence, the model generates something like this:
The capital of France is Paris. Paris has been the capital since the 10th century and is the largest city in France. Answer: Paris
The parser finds the Answer: line, extracts “Paris”, and matching succeeds.
With " " as the stop sequence, the model generates:
The capital of France is Paris.
And then it stops. The first newline character triggers the stop. The model never gets to write its second line, let alone the Answer: line.
The model knows the answer. It was saying the answer. The stop sequence just cut it off before it could finish, and the scoring pipeline treated the result as a failure.
Took Away From This
The stop sequence is not changing what the model knows. It is changing what the model is allowed to say. The scoring pipeline then reports the truncated result as if it reflects model quality, and anyone reading the benchmark has no idea that the score was determined by a config string.
This creates a real problem for reproducibility. If Harness A uses a newline stop and Harness B uses no stop, they will produce completely different accuracy numbers from the same model on the same prompts. But nobody would notice, because stop sequences are almost never reported.
I think the fix is simple: treat the stop sequence as an experimental parameter. Report it alongside the model name, prompt template, and decoding settings. If you are using chain-of-thought or any multi-line output format, verify what your stop sequence actually does to the output before trusting the final score.
