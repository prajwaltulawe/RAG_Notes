How We Handle 10,000 Concurrent Streaming LLM Requests on a Budget
Our AI writing assistant went viral on a Tuesday.
By Wednesday afternoon, we had 10,000 people hitting the “Generate” button at the exact same time. It felt like a massive win, until I looked at our AWS bill projections and our Datadog alerts.
Our servers were on fire. Not because the LLM inference was hard, but because our infrastructure was melting under the weight of 10,000 open network connections.
Here is the dirty secret about streaming LLMs that most tutorials don’t tell you: Your server doesn’t crash because of the AI math. It crashes because holding open 10,000 persistent HTTP connections is incredibly expensive.
If you just spin up a standard API and start streaming tokens from OpenAI, your RAM will max out, your CPU will choke on context switching, and your cloud provider will charge you a fortune for idle network overhead.
We couldn’t afford to throw money at the problem. We had to outsmart it. Here is the exact, budget-friendly architecture we use to stream responses to 10,000 concurrent users without breaking the bank.
The Problem: The “Holding the Door Open” Trap
When you stream an LLM response, you are sending text to the user token by token. This usually takes 5 to 15 seconds.
During those 15 seconds, your backend has to hold a network connection open to the user’s browser, and hold a connection open to the OpenAI API. If you do this synchronously (like in standard Flask or Django), a single worker process is frozen. It sits there doing absolutely nothing, just waiting for OpenAI to send the next 4 bytes of text.
Multiply that “doing nothing” by 10,000 users, and you need a massive, over-provisioned fleet of servers just to hold the doors open.
To fix this, we had to change the rules of the network layer.
Fix 1: Ditch WebSockets. Use True Server-Sent Events (SSE)
The first mistake most teams make is reaching for WebSockets. WebSockets are bidirectional. They are great for chat apps or multiplayer games, but they are absolute overkill for a one-way stream of text from an LLM. WebSockets require complex upgrade handshakes and persistent state management.
We switched entirely to Server-Sent Events (SSE) over standard HTTP. It’s vastly cheaper on memory and natively supported by every browser.
But you cannot use a standard synchronous web framework to do SSE at scale. You must use an asynchronous framework like FastAPI with Python’s asyncio.
Here is the exact pattern we use to stream tokens without blocking our server:
from fastapi import FastAPI from fastapi.responses import StreamingResponse from openai import AsyncOpenAI import asyncio app = FastAPI() client = AsyncOpenAI(api_key="your-key") async def generate_stream(prompt: str): """An async generator that yields chunks as they arrive.""" # Notice: No 'await' on the iterator itself in older versions, # but AsyncOpenAI handles the async iteration perfectly now. stream = await client.chat.completions.create( model="gpt-4o-mini", # We'll talk about model choice next messages=[{"role": "user", "content": prompt}], stream=True ) try: async for chunk in stream: if chunk.choices[0].delta.content is not None: # Yield the raw string. FastAPI handles the SSE framing. yield chunk.choices[0].delta.content finally: # CRITICAL: Always clean up. If the user closes their browser # mid-stream, this ensures the connection dies cleanly on your server. await stream.close() @app.get("/generate") async def stream_endpoint(prompt: str): return StreamingResponse( generate_stream(prompt), media_type="text/event-stream" )
Why this saves money: Because generate_stream is an async generator, FastAPI can put it to sleep while waiting for OpenAI. That single worker is now free to handle other users’ requests while it waits. We went from needing 500 server workers to handling 10,000 streams on just 40 workers.
Fix 2: The “LiteLLM” Load Balancer
OpenAI’s rate limits are ruthless. If 10,000 people hit your app simultaneously, and you funnel all of them through a single OpenAI API key, you are going to get slammed with 429 Rate Limit errors.
Buying a higher tier in OpenAI is expensive. Instead, we implemented a local gateway using LiteLLM.
LiteLLM is an open-source proxy that sits between your FastAPI app and the LLM providers. It translates requests so you can treat every model identically. But its superpower is Load Balancing.
We buy 4 standard OpenAI API keys (tier 1). We point LiteLLM at all 4 keys and set it to routing_strategy: "least-busy".
When 10,000 requests hit our server:
1.
FastAPI handles the async streaming.
2.
The request goes to our local LiteLLM proxy.
3.
LiteLLM silently splits the traffic across 4 keys, automatically rotating if one gets rate-limited.
We effectively multiplied our OpenAI throughput by 4 for the price of a $20/month basic tier accounts, rather than spending thousands to upgrade our enterprise tier.
Fix 3: The “Budget” Secret - Semantic Routing
This is where we actually saved real money. Not all prompts are created equal.
When a user asks, “Summarize this 2-page article,” that requires GPT-4o. When a user asks, “Write a haiku about a cat,” using GPT-4o is literally burning dollar bills for no reason.
We built a tiny, local classification model (using scikit-learn, running in milliseconds) at the very top of our FastAPI endpoint. It categorizes incoming prompts into COMPLEX or SIMPLE.
•
If SIMPLE: We route the stream to a self-hosted Llama-3–8B model running on a single, cheap AWS g5.xlarge GPU instance using vLLM. Cost: $0.00 per request.
•
If COMPLEX: We route the stream through LiteLLM to OpenAI gpt-4o-mini or gpt-4o.
By offloading roughly 40% of our trivial requests to a cheap local GPU, we cut our OpenAI API bill by nearly half, and - more importantly - we reduced the concurrent load on our OpenAI connection pool by 40%, practically eliminating our rate limit errors.
Stop Over-Provisioning for AI
The reflex action when your AI app gets popular is to throw more RAM, more CPU, and more money at your cloud provider.
But streaming is an I/O bound problem, not a compute problem. You don’t need bigger servers. You need smarter code.
If you adopt async generators to free up your workers, put a proxy like LiteLLM in front of your API keys to distribute the load, and stop using a $10 LLM to write cat poems, you can handle massive, viral scale on a startup budget.
