LLM ChatCompletion System Prompt Inconsistency Issue & How to Improve Conversational RAG Systems
I was working on conversational RAG systems and discovered a consistency issue in chat completion LLMs that can occur in poorly implemented RAG systems.
TL;DR: Don’t change the system message as the context progresses—aka, don’t put RAG-retrieved context in system messages for chat completion.
❌ Don’t do this:
messages = [ { 'role': 'system', # note, as the conversation progresses, this system message changes. Because we retrieve new context at every step 'content': "Use the following context to answer the user questions and nothing else: {context}" }, { 'role': 'user', 'content': "q1", }, { 'role': 'assistant', 'content': "r1", }, { 'role': 'user', 'content': "q2", }, ]
✅ Do this:
messages = [ { 'role': 'system', # don't use a system message 'content': "" }, { 'role': 'user', 'content': "Use the following context to answer the user questions and nothing else: {context}. Conversation history: {history}. Current question: {question}", }, ]
→ LangChain’s conversational RAG is a good standard to follow.
The rest of this blog explains why dynamically changing the system message in chat completion is a bad idea. I start with the problem definition, experimental observations with GPT-4, and end by showing how the chat completion language modeling fine-tuning loss is optimized for a static system message for the same chat. (Of course, you can change the system prompt across different chats.)
Conversational RAG

1.
Append each new user and assistant message as separate user-assistant messages and change the context in the system prompt:

Consistency Issue:
Either by manually modifying previous assistant responses or by changing the system prompt as the conversation proceeds, the LLM gets confused. Here’s the LLM’s dilemma:
Does it (the LLM) generate responses consistent with previous assistant messages (its own generations) or generate responses consistent with the system message instructions?
Consistency Issue in Conversational RAG Systems:
Let’s take an example:
messages = [ { 'role': 'system', 'content': "Alice's best friend is Bob but Bob's best friend is Eve." }, { 'role': 'user', 'content': "Who is Alice's best friend?", }, ]
GPT-4 Response: Alice’s best friend is Bob.
messages = [ { 'role': 'system', # note the system prompt has changed 'content': "Alice's best friend is Eve but Bob's best friend is Alice." }, { 'role': 'user', 'content': "Who is Alice's best friend?", }, { 'role': 'assistant', 'content': "Alice's best friend is Bob." }, { 'role': 'user', 'content': "Who is Alice's best friend?", }, ]
GPT-4 Response: ??
In the latter example, the previous assistant response is incorrect because the context in the system prompt has changed. Is the LLM supposed to stay consistent with its previous responses or follow the system prompt instructions?
LLMs are neural networks (NNs), and NNs are not explainable.
According to many, almost everything trying to explain such responses and all prompt hacks are pseudo-science (analogous to how Richard Feynman called most of psychology pseudo-science because the human brain is not very interpretable). I’m bullish on a breakthrough idea for explainable NNs in the future. LLMs are text-in-text-out machines. Looking at how these models are trained with system prompts (open models only, fuck OpenAI) gives some insights. I present them at the end; for now, let’s focus on fixing conversational RAGs.
If you’re working on enterprise conversational-RAG solutions, such conflicting scenarios will be very common. Let’s look at another, more formal, LLM system message instruction disobedience example, but before that, a trivial example:
A trivial inconsistency problem:
messages = [{'role': 'user', 'content': """Just reply with "A" Just reply with "B" """}]
Does the LLM respond with “A” or with “B”?
This question is uninteresting. One might say the latter instruction (say B) should take precedence over the prior (say A), so it must respond with B. Pseudo-science! As a human, we would say “inconsistent” or just scoff at whoever’s asking and move on. Doesn’t matter.
What I present is a more interesting problem, I reiterate:
Does it (LLM) generate responses consistent with previous assistant messages (its own generations) or generate responses consistent with the system message instructions?
The answer is to use chat completion APIs such that:
1.
If a system message exists, it must not change as the conversation progresses
2.
You never modify previous assistant responses

Now let’s build some fake history such that it doesn’t follow the instructions and responds with numerical outputs (e.g., 2). This is what happens when we use RAG and impute the context in the system prompt! Imagine asking the LLM to “Only use the information in the given context”. In such a scenario, previous LLM responses will always be using info from previous system prompt contexts and hence will be violating the system prompt instructions. As the conversation progresses, the LLM will start doing what it has been doing (not following the context constraint) and start hallucinating! Thus, changing the system prompt as the conversation progresses is a bad idea. So what’s the alternative?

Chat Finetuning:
To understand this better, let’s take a look at chat finetuning models. We don’t know how OpenAI chat finetunes, but we can take a look at open sourced models.
Following is the Llama2 Chat template:
[INST] &lt;> {your_system_message} &lt;> {user_message_1} [/INST] {model_reply_1}[INST] {user_message_2} [/INST] {model_reply_2}[INST] {user_message_3} [/INST]
While finetuning, the model’s loss is computed ONLY over the model replies. In pre-training you would compute the loss over every single token. However, in chat finetune, you compute the loss over “model_reply_1”, “model_reply_2” and mask all other tokens with -1.
Look at Axolot’s Llama2 training scripts for example. The system prompt and all user messages are replaced with IGNORE_INDEX for loss compute. Thus, the model is expected to generate {model_reply_1}, {model_reply_2} and so on with the given system and user messages. The training loss is designed such that all (current and previous) assistant messages can be generated with user messages and a static system prompt.
Thus - DO NOT change system messages as conversation progresses.
This is probably obvious to many, but to others, it’s always interesting to look under the hood. I hope you learned something.
