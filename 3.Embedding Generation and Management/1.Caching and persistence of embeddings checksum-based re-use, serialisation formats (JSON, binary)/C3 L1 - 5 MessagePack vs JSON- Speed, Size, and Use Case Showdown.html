JSON vs. MessagePack: A 6x Performance Leap on my AMD Ryzen
In the modern IT landscape, cost efficiency is the anchor that keeps companies afloat and competitive. Over the last two decades, the most successful organizations have stayed ahead of the curve by aggressively minimizing infrastructural overhead. As reliance on third-party cloud providers like AWS and GCP has skyrocketed, two hurdles have become dominant: the cost of compute operations and the cost of data storage.
After encountering discussions regarding the efficiency of binary formats like Protobuf and MessagePack, I was compelled to dive deeper. My goal was to move beyond the theory and measure exactly how much these serialization methods can impact performance and, ultimately, the bottom line.
We have all relied mainly on JSON as the suitable means for data transfer over an internet connection. The reason for this is that it is human-readable and supports every programming language. However, this comes at the cost of bloatness. This bloatness appears in several formats:
•
Verbosity: Quotes, braces, and commas are used throughout, which take up unnecessary space.
•
CPU Overhead: JSON must be translated and processed by the CPU; it operates at a much higher level than binary, requiring more effort to parse.
•
Binary Bloat: When sending a file or large attachments, JSON needs to encode it (usually in Base64), which significantly increases the size of the data being transferred.
So the logical decision to make is to find a way to strip off what is unnecessary and send only what is needed. However, a step beyond that is to identify points where you do not necessarily need to read the JSON transfer yourself - and here comes MessagePack.
It is like JSON but binary, which makes it great for serialization: faster and smaller. Looking at the raw data, you will not understand it because it is in a computer-readable format.
How does it work? Its secret lies in how it handles data headers. In JSON, a number like 100 takes up three bytes because it is stored as three separate text characters (‘1’, ‘0’, ‘0’). However, MessagePack recognizes that 100 can fit into a single 8-bit format, so it is stored as just one byte.
To see if this theoretical ‘one-byte’ efficiency actually translates to real-world performance, I ran a series of benchmarks on an AMD Ryzen 5 3550H. I compared the standard Go JSON library against MessagePack to see the difference in speed and memory management.
Using Golang, I wrote four APIs: two that returned a JSON response and two that returned a MessagePack response. The tests carried out compared the results of sending small payloads with simple text against large payloads containing an image. Here are the results:
Test 1: Small Data Structures
•
JSON: 4,452 ns/op | 944 B/op | 12 allocs/op
•
MessagePack: 3,996 ns/op | 992 B/op | 8 allocs/op
Test 2: Large Payloads (Images)
•
JSON: 272,747 ns/op | 140,479 B/op | 2 allocs/op
•
MessagePack: 43,732 ns/op | 106,682 B/op | 4 allocs/op
To move beyond theory, I ran the above benchmarks on my AMD Ryzen 5 3550H. The output from the Go benchmark tool gives us a clear look at how “bloatness” impacts both speed and memory.
Why These Numbers Matter
Looking at these results, a few things stand out that directly affect the cost of running an application:
1. The 6x Speed Advantage In the image test, MessagePack was over 6 times faster (43k ns vs 272k ns). This is because JSON has to work hard to encode binary data into text. In a world of “Serverless” functions where you are billed by the millisecond, reducing your execution time by 80% is a massive win.
2. The 33% “Base64 Tax” Notice the memory usage for the image test. JSON used 140KB while MessagePack used 106KB. That extra 34KB is purely “bloatness” created by converting the image to text. When you scale this to millions of requests, you are paying your cloud provider to move and store “air” - useless text data that adds no value to the end user.
3. Memory Efficiency Even though MessagePack uses a few more allocations in the image test, the total bytes allocated is significantly lower. This keeps your application’s memory footprint small, allowing you to stay on cheaper, smaller server instances for longer.
Choosing the Right Tool: Trade-offs and Use Cases
While the benchmarks show a clear win for MessagePack in terms of performance and “bloatness,” choosing between the two depends on where the data is going and who needs to read it.
JSON: The Web Standard
Use Cases:
•
Public APIs: If your API is meant to be used by third-party developers, JSON is the best choice because everyone knows how to use it.
•
Web Browsers: JavaScript handles JSON natively. It is the natural language of the front-end.
•
Debugging: When you need to see exactly what is being sent in your logs without extra tools.
The Trade-off: You trade performance and cost for convenience and compatibility.
MessagePack: The Efficiency King
Use Cases:
•
Microservices: When your own servers are talking to each other (Internal APIs), there is no reason to use slow, bloated text.
•
Mobile Apps: For apps that need to be fast and save on a user’s data plan, MessagePack’s smaller payload size is a huge advantage.
•
Image & Binary Heavy Apps: As my benchmarks showed, if you are moving images or files, MessagePack is over 6x faster and 33% smaller.
•
IoT & Low-Power Devices: Devices with limited CPU (like my Ryzen 3550H test showed) benefit from the lower processing requirements.
The Trade-off: You trade human-readability for massive speed and cost savings.
The “logical decision” I mentioned at the start comes down to this: if your goal is to keep your company competitive by maintaining low infrastructural costs, you cannot ignore the efficiency of binary formats.
By switching to MessagePack for internal data transfers, we don’t just “save a few bytes.” We significantly reduce CPU overhead and eliminate the “Base64 Tax” on our cloud egress bills. In a world where every millisecond and every gigabyte counts toward your bottom line, cutting the bloat is no longer optional, it’s essential.
