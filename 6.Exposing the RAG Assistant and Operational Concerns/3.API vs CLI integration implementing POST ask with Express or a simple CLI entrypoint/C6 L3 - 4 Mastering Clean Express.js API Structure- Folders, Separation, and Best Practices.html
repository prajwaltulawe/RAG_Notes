How I Set Up a Clean Express.js API (Step by Step)
Stop Writing Messy Backends: Here’s the Structure That Saved My Sanity
The first Express.js API I built worked.
Technically.
It returned JSON.
It connected to the database.
It even handled authentication.
It was also a disaster.
Routes everywhere.
Business logic inside controllers.
Controllers inside route files.
A random utils.js that became a dumping ground for everything I didn’t understand.
No structure.
No boundaries.
Just vibes.
Three months later, I was scared to touch my own code.
That was the moment I realized something important:
Express is minimal.
That’s a feature.
But if you don’t design your structure intentionally, it becomes chaos.
This article is exactly how I now set up a clean,
scalable Express.js API step by step based on real production experience,
painful refactors, and honest mistakes.
No fluff.
No overengineering.
Just structure that works.
Step 1: Start With Intentional Project Structure
Before writing a single endpoint, I create structure.
Here’s the folder layout I use almost every time:
src/ ├── config/ ├── controllers/ ├── services/ ├── routes/ ├── middlewares/ ├── models/ ├── utils/ ├── app.js └── server.js
Simple.
Predictable.
Clean.
Why this matters?
Because future you is tired.
Future you doesn’t want to hunt for logic across random files.
Reality check: If your project has more than 5 endpoints and everything lives in index.js, you are building technical debt.
Step 2: Separate App From Server (This Is Non-Negotiable)
Most beginners do this:
const express = require('express'); const app = express(); app.listen(3000);
It works.
But it destroys testability.
Instead, I separate them.
app.js
const express = require('express'); const app = express(); app.use(express.json()); module.exports = app;
server.js
const app = require('./app'); const PORT = process.env.PORT || 3000; app.listen(PORT, () => { console.log(`Server running on port ${PORT}`); });
Why?
Because now I can import app into test files without starting the server.
Small decision.
Massive long-term payoff.
Step 3: Environment Variables Done Properly
Never hardcode configuration.
Not ports.
Not database URLs.
Not JWT secrets.
I use dotenv:
npm install dotenv
In server.js:
require('dotenv').config();
And I create a .env file:
PORT=3000 DATABASE_URL=your_database_url JWT_SECRET=supersecret
Then I centralize config in config/index.js:
module.exports = { port: process.env.PORT, dbUrl: process.env.DATABASE_URL, jwtSecret: process.env.JWT_SECRET };
Why centralize config?
Because scattered process.env calls make debugging painful.
If configuration is everywhere, mistakes are invisible.
Step 4: Routes Should Be Boring
If your routes contain logic, you’re doing it wrong.
Routes should only map HTTP to controller.
Example:
routes/user.routes.js
const express = require('express'); const router = express.Router(); const userController = require('../controllers/user.controller'); router.post('/', userController.createUser); router.get('/:id', userController.getUser); module.exports = router;
That’s it.
No business logic.
No database queries.
No validation rules.
Just wiring.
Step 5: Controllers Are Traffic Managers
Controllers should not contain business logic either.
They:
•
Receive request
•
Call service
•
Send response
Example:
const userService = require('../services/user.service'); exports.createUser = async (req, res, next) => { try { const user = await userService.createUser(req.body); res.status(201).json(user); } catch (error) { next(error); } };
Notice what’s missing?
No database code.
No validation rules.
No password hashing.
Controllers orchestrate.
They don’t think.
Step 6: Services Contain Business Logic
This is where real logic lives.
const User = require('../models/user.model'); const bcrypt = require('bcrypt'); exports.createUser = async (data) => { const existingUser = await User.findOne({ email: data.email }); if (existingUser) { throw new Error('User already exists'); } const hashedPassword = await bcrypt.hash(data.password, 10); const user = await User.create({ ...data, password: hashedPassword }); return user; };
This separation does something powerful:
You can now test business logic independently.
You can replace Express tomorrow and keep services intact.
That’s clean architecture thinking even inside a simple Express app.
Step 7: Global Error Handling (Stop Repeating Try/Catch Everywhere)
I used to wrap every route with try/catch.
Exhausting.
Instead, create an error middleware.
app.use((err, req, res, next) => { console.error(err); res.status(500).json({ message: err.message }); });
Now controllers just call next(error).
Cleaner.
Centralized.
Maintainable.
Step 8: Add Middleware Like a Professional
Logging, security, validation not optional.
I almost always install:
•
helmet
•
cors
•
morgan
npm install helmet cors morgan
In app.js:
const helmet = require('helmet'); const cors = require('cors'); const morgan = require('morgan'); app.use(helmet()); app.use(cors()); app.use(morgan('dev'));
Security headers.
Clean logs.
Cross-origin support.
Production-ready foundation.
Step 9: Version Your API
This is underrated.
Instead of:
/api/users
Do this:
/api/v1/users
Future changes won’t break clients.
Backward compatibility matters.
Step 10: Keep It Boring. Seriously.
Developers love complexity.
“Let’s add CQRS.”
“Let’s add event sourcing.”
“Let’s add dependency injection framework.”
Relax.
Most APIs need clarity, not cleverness.
A clean Express API is not about patterns.
It’s about boundaries.
My Non-Negotiable Rules
1.
No logic in routes
2.
Minimal logic in controllers
3.
Business rules in services
4.
Centralized config
5.
Global error handling
6.
Clear folder structure
If a file grows beyond 300-400 lines, I refactor.
If a function is doing too much, I split it.
If I hesitate before editing something, I redesign it.
Fear is a code smell.
Final Thoughts
Express doesn’t enforce structure.
That’s your job.
You can build a beautiful API.
Or you can build a future nightmare.
The difference is discipline.

Architecture debates make us better engineers.
