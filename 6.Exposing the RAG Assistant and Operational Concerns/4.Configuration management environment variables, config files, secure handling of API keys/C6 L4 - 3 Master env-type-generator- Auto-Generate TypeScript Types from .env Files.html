Stop Writing TypeScript Types for Environment Variables Manually
How a simple CLI tool can eliminate type errors, boost developer productivity, and catch configuration bugs before they hit production
The Problem Every TypeScript Developer Faces
You’re building a TypeScript application. You’ve got your .env file set up with database URLs, API keys, and feature flags. You try to access an environment variable:
const dbUrl = process.env.DATABASE_URL; const poolSize = process.env.DATABASE_POOL_SIZE;
TypeScript reports no errors. Your IDE shows no warnings. Everything looks fine… until you deploy to production and discover:
•
You misspelled DATABASE_URL as DATABSE_URL somewhere in your code
•
You forgot to set DATABASE_POOL_SIZE in your production environment
•
You’re trying to use a number stored as a string without proper parsing
Sound familiar? You’re not alone. This is one of the most common sources of runtime errors in TypeScript applications.
The Traditional Solutions (And Their Problems)
Most developers solve this problem in one of three ways:
1. Manual Type Declarations
// env.d.ts declare namespace NodeJS { interface ProcessEnv { DATABASE_URL: string; DATABASE_POOL_SIZE: string; STRIPE_SECRET_KEY: string; // ... 50 more variables } }
The problem: You have to maintain two sources of truth (.env and env.d.ts). Add a new variable? Update both files. Remove one? Remember to delete it from both places. It’s tedious, error-prone, and developers simply don’t do it consistently.
2. Runtime Validation Libraries
import { z } from 'zod';
const envSchema = z.object({ DATABASE_URL: z.string().url(), DATABASE_POOL_SIZE: z.string().transform(Number), STRIPE_SECRET_KEY: z.string(), });
export const env = envSchema.parse(process.env);
The problem: This gives you runtime validation (great!), but you still have to manually write the schema. It’s verbose, requires understanding Zod/Yup/Joi, and again - you’re maintaining two sources of truth.
3. Third-Party Environment Management
Libraries like t3-env or envalid require you to define schemas upfront:
import { createEnv } from "@t3-oss/env-core"; import { z } from "zod";
export const env = createEnv({ server: { DATABASE_URL: z.string().url(), DATABASE_POOL_SIZE: z.string(), }, });
The problem: Same issue - you’re defining everything manually. These tools are excellent for what they do, but they don’t solve the fundamental problem: why should you have to write out all your environment variables again?
Introducing env-type-generator
What if your TypeScript types could be automatically generated from your .env file? What if you could get type safety, IDE autocomplete, and runtime validation without writing a single type definition?
That’s exactly what env-type-generator does.
Zero Config, Maximum Impact
Install the package:
npm install --save-dev env-type-generator
Run one command:
npx env-type-gen
That’s it. You now have type-safe environment variables with full IDE autocomplete support.
How It Works
env-type-generator parses your .env files and automatically generates TypeScript type definitions. Let’s walk through an example.
Your .env File
# Database Configuration DATABASE_URL=postgresql://localhost:5432/mydb DATABASE_POOL_SIZE=10
# API Keys STRIPE_SECRET_KEY=sk_test_xxx STRIPE_PUBLISHABLE_KEY=pk_test_xxx
# Feature Flags ENABLE_ANALYTICS=true MAX_UPLOAD_SIZE_MB=50
Generated Types (Automatic)
declare namespace NodeJS { interface ProcessEnv { /** Database Configuration */ DATABASE_URL?: string | undefined; DATABASE_POOL_SIZE?: number | undefined;
/** API Keys */ STRIPE_SECRET_KEY?: string | undefined; STRIPE_PUBLISHABLE_KEY?: string | undefined;
/** Feature Flags */ ENABLE_ANALYTICS?: boolean | undefined; MAX_UPLOAD_SIZE_MB?: number | undefined; } }
Notice several things:
1.
Comments are preserved from your .env file as JSDoc comments
2.
Types are inferred automatically (10 becomes number, true becomes boolean)
3.
No manual maintenance required - change your .env, regenerate types
Type Safety in Action
Now when you use environment variables:
// ✅ Autocomplete works! const dbUrl = process.env.DATABASE_URL;
// ✅ TypeScript knows it's a number const poolSize = process.env.DATABASE_POOL_SIZE;
// ❌ TypeScript catches typos const invalid = process.env.DATABSE_URL; // Error: Property 'DATABSE_URL' does not exist
Advanced Features for Production Applications
While the basic usage is powerful, env-type-generator includes several advanced features for enterprise applications:
1. Runtime Validation with Zod
Generate both types AND runtime validation schemas:
npx env-type-gen --validation-lib zod --parse-types
This creates two files:
•
env.d.ts - TypeScript definitions
•
env.validator.ts - Zod schema with runtime validation
// Auto-generated env.validator.ts import { z } from 'zod';
export const envSchema = z.object({ DATABASE_URL: z.string().url(), DATABASE_POOL_SIZE: z.string().transform((val) => Number(val)), ENABLE_ANALYTICS: z.enum(["true", "false"]).transform((val) => val === "true"), });
export const env = envSchema.parse(process.env);
Now your app will fail fast at startup if environment variables are missing or invalid - no more discovering configuration issues in production.
2. Required Variables
Mark critical variables as required:
npx env-type-gen --required DATABASE_URL STRIPE_SECRET_KEY
Or use strict mode to require ALL variables:
npx env-type-gen --strict
3. Watch Mode for Development
During development, regenerate types automatically when your .env changes:
npx env-type-gen --watch
4. Multiple Environment Files
Handle different environments seamlessly:
npx env-type-gen --env-files .env .env.local .env.production
5. Configuration File
For complex projects, use a configuration file:
// env-type.config.js module.exports = { envFiles: ['.env', '.env.local'], outputPath: './src/types/env.d.ts', validationLib: 'zod', validationOutput: './src/config/env.validator.ts', requiredVars: ['DATABASE_URL', 'API_KEY'], parseTypes: true, strict: false, };

Best Practices and Recommendations
Based on production usage, here are our recommendations:
1. Don’t Commit Generated Files
# .gitignore src/types/env.d.ts src/config/env.validator.ts
Generate them as part of your build process instead.
2. Generate Before Build
{ "scripts": { "prebuild": "env-type-gen --validation-lib zod --strict", "build": "tsc" } }
3. Use Strict Mode in Production
Catch missing variables early:
env-type-gen --strict --required DATABASE_URL API_KEY SECRET_KEY
4. Leverage Comments
Document your environment variables in .env.example:
# Database connection string (format: postgresql://user:pass@host:port/db) DATABASE_URL=postgresql://localhost:5432/mydb
# Maximum concurrent database connections (recommended: 10-50) DATABASE_POOL_SIZE=10
These comments become JSDoc in your generated types.
5. Run in Watch Mode During Development
{ "scripts": { "dev": "concurrently \"env-type-gen --watch\" \"next dev\"" } }
Under the Hood: The Technical Implementation
For those interested in how it works:
1.
Parsing: Uses dotenv to parse .env files
2.
Type Inference: Analyzes values to determine types (numbers, booleans, JSON objects)
3.
Code Generation: Generates TypeScript AST and formats output
4.
Validation Schema: Optionally generates Zod/Yup/Joi schemas
5.
Watch Mode: Uses chokidar for file system watching
The entire package is written in TypeScript, fully tested, and has zero runtime dependencies in production (it’s a dev tool).
