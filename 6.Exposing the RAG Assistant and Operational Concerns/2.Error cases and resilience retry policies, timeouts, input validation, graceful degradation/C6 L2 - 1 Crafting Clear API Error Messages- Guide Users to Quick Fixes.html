Designing a Great API: Error Messages
The technology behind an API must increase its usability, not its complexity
I’m honored to be attending the Nordic APIs 2018 Platform Summit this week as a representative of the team that built the AvaTax REST API. With our nomination in their 2018 API contest (Voting is still open!), I’d like to set down some of the great features and design principles that made the AvaTax API what it is today.
I imagined when I sat down to write this that I would spend time talking about our programming language and platform (we use C# with Microsoft DotNetCore), or the server platform (AWS), or the database layer (Dapper and AutoMapper) - but instead I’m going to talk about error messages.
Useful Error Messages
Back in July 2016, based on a request by one of my colleagues, we set out to give the new API a standard set of error messages. Each error message must be clearly written, and it must explain what went wrong and how the customer can fix things.
This wasn’t how I expected to spend my time. I thought I’d be working on Model-View-Controller, or creating a great new data layer, or writing complex functions to help people query for the data they needed. But the more I studied the implementation of my API, the more I realized that error codes were critical.
{ "code": "TaxpayerNumberRequired", "target": "Unknown", "details": [ { "code": "TaxpayerNumberRequired", "number": 9, "message": "taxpayerIdNumber is required for customers subscribing to Avalara Returns.", "description": "Customers who have an active MRS or CSP service must provide taxpayerIdNumber for all company records.", "faultCode": "Client", "helpLink": "http://developer.avalara.com/avatax/errors/TaxpayerNumberRequired", "severity": "Error" } ] }
Who would understand this kind of a problem without a clear error code? People aren’t born knowing this stuff. Our goal is to help people calculate their taxes and file them automatically, and they don’t want to have to think about it.
Why is this error message useful?
•
It leads with the most important information: taxpayerIdNumber is required.
•
It explains why it’s required: for customers subscribing to Avalara Returns.
•
It explains what you have to do - you must fill in this field for all company records.
•
It gives you a link to a helpful page with more information.
•
The error message is broken down into separate fields, so the UX designer can choose what parts to display.
All of this information is critical for someone learning a new API. When I first began writing Windows apps back in the early 1990s, I didn’t know how to find out that 0x00000591 meant that my display context handle was invalid. Back then, constant research and buying Charles Petzold’s books was the only way to solve the problem.
Now, twenty eight years later, I was building a tax API. Since nobody really likes writing software to handle taxes, and since Charles Petzold wasn’t available, I had to make sure my error messages clearly provide guidance for a new developer.
It wasn’t always easy.
Just Plain Bad Error Messages
Error messages aren’t good unless you spend time and effort making them this way. I once found a pull request that included an interesting new error message. I can’t find it anymore, but the error message looked a bit like this:
"code": "CodeNotFoundInHash", "message": "The code was not found in the hash.", "description": "The field `code` requested did not match any entries in the dictionary.", "faultCode": "Client",
The programmer was being careful. They had put a try/catch block around a bit of code that could fail, and they had dutifully created a custom error message to use if an exception occurred. They even wrote both a short and a long description.
But you’ll notice a few things:
•
Why was the code requested not found in the dictionary, or hash?
•
Was the dictionary or hash something the customer created?
•
Why is the fault code “Client”?
•
What should the customer do about it?
This error could only occur if something about our system was not working right. It could never be caused by the customer themselves; it exposed a design flaw in our system. So how should we handle it?
Logging to Slack
I worked with the developer above to remove the error message. In his use case, this problem was simply unrecoverable. He had stored data into a system and then fetched it back. If the data couldn’t be retrieved back, the system had failed. The only possible solution was to log the failure and warn the team that something had gone wrong.

Our team immediately sees every error, and we have a wealth of information available to make the debugging work easier. We immediately build a test to ensure that the problem can be reproduced, and we escalate a hotfix to address the root cause.
Each case is different, but we often discover interesting things about our system:
•
A customer might be configured differently in one side of the system from another
•
A customer may have stored some data and then cancelled part of their subscription, leaving them in a complex state
•
One side of an interface may have been upgraded before the other side was ready to handle it
There are many other critical elements of a great API, including consistency, conveyance, technology, documentation, and security (the one principle above all) - but in the case of our tax API, error messages became one of our defining features. We made each error message friendly and useful to our developers and our partners, and they returned the favor by being our customers.
Thank you all for the privilege to have built this API!
